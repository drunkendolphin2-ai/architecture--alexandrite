## Выбор и настройка мониторинга в системе

### Мотивация
Сейчас компания узнаёт о проблемах с заказами слишком поздно - из жалоб клиентов, операторов и B2B-партнёров. После открытия внешнего API Яндекс Метрика перестала давать полную картину, потому что значительная часть заказов приходит не через сайт, а через API.

Мониторинг нужен, чтобы:
- видеть количество заказов на каждом этапе жизненного цикла
- заранее обнаруживать зависшие, просроченные и близкие к просроченным заказы
- понимать, где возникает задержка: Internet Shop, CRM, MES, RabbitMQ, БД или внешнее API
- снизить количество ручных разборов по жалобам клиентов
- дать бизнесу объективные SLA/SLO по обработке заказов
- быстрее реагировать на рост нагрузки и не терять клиентов

Если это реализовать, то компания получит
- меньше потерянных и зависших заказов
- быстрее реакция на проблемы и инциденты
- меньше жалоб в поддержку
- меньше риск потери клиентов и партнеров
- понимание, где есть точки оптимизации системы


### Выбор подхода к мониторингу
| Компонент            | Подход                 | Обоснование                                                          |
|----------------------|------------------------|----------------------------------------------------------------------|
| Shop API             | Четыре золотых сигнала | Это пользовательский API, важны latency, traffic, errors, saturation |
| CRM API              | Четыре золотых сигнала | Продавцы работают с заказами, важно видеть деградацию API            |
| MES API              | Четыре золотых сигнала | Операторы жалуются на медленную страницу, важна latency и saturation |
| RabbitMQ             | USE                    | Важны возраст сообщений, размер очереди, DLQ, утилизация             |
| Базы данных          | USE                    | Для БД важны utilization, saturation, errors, locks                  |
| Сервисы              | USE                    | CPU, memory, GC, thread pools, connection pools                      |
| Хранилище 3D-моделей | USE                    | Важны объём, ошибки загрузки/чтения, latency операций                |

### Метрики

#### Shop, CRM, MES, B2B API
| Метрика                                 | Почему                                                                                  | Лейблы                                                   |
|-----------------------------------------|-----------------------------------------------------------------------------------------|----------------------------------------------------------|
| Number of requests (RPS) for  API       | Нужно понимать какая нагрузка есть на API                                               | service, method, endpoint, client_type, env              |
| Response time (latency) for  API        | Нужно понимать, как долго мы отвечаем                                                   | service, method, endpoint, client_type, env              |
| http_responses_total                    | Хотим иметь метрику в целом по ответам, в лейблах - код ответа                          | service, method, endpoint, client_type, env, status_code |
| Kb tranferred (received) for API        | Хотим знать объем трафика                                                               | service, method, endpoint, client_type, env              |
| Kb provided (sent) for   API            | Хотим знать объем трафика                                                               | service, method, endpoint, client_type, env              |
| Number of simultanious sessions for API | Это будет показателем насыщенности                                                      | service, instance, env                                   |

Для B2B API можно добавить client_id, поскольку количество партнеров не сильно большое и можно не бояться за кардинальность

### План действий
1) Развернуть time-series БД (Prometheus или VictoriaDB), Grafana. Нужны на каждом окружении
2) Научить приложения откидывать метрики, например micrometer и Spring Boo Actuator для Java приложений
3) Подключить экспортеры метрик для Rabbit и Postgresql
4) Внедрить бизнес-метрики в приложения
5) Собрать дашборды для продактов, разработчиков и поддержки
6) Создать алерты, зафиксировать SLO, настроить каналы доставки алертов, назначить дежурных
