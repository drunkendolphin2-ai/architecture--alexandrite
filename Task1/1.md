## Планирование: анализ, идентификация проблем и поиск решений

### Проблемные места
1. Сильная связность систем через прямой доступ к чужим данным. У CRM нет собственного хранилища: CRM API работает напрямую с Shop DB.
2. Жизненный цикл заказа размазан между Shop, CRM и MES. При этом нет механизма сверки, конфликты накапливаются и не решаются
3. Событийная интеграция через RabbitMQ недостаточно надёжна и наблюдаема. В случае сбоев и ошибок - заказ просто теряется, помимо этого без мониторинга невозможно понять, есть ли проблемы
4. MES-дэшборд медленно показывает заказы из-за неоптимальной модели чтения. Нет кэша, нет реплики на чтение. Сами запросы могут быть неоптимальны
5. Внешний API открыт без достаточного управления нагрузкой.
6. Базы данных и приложения имеют по одному инстансу, что создаёт риск отказа и ограничивает масштабирование.
7. Нет верхнеуровневого мониторинга статуса заказов: компания узнаёт о проблемах из жалоб.
8. CI/CD и ручной QA замедляют доставку исправлений в production.
9. MES вместо расчета стоимости - сам создает заказ, нужно развязать его и создание заказа

### Инициативы
1. Мониторинг и алертинг по всем компонентам:
   - мониторинг
   - логи
   - трейсинг с orderId
   Почему: без этого не знаем, где заказы теряются.

2. Надёжная событийная обработка заказов:
   - outbox паттерн в магазине и CRM - чтобы решить проблему dual write
   - CRM API нужно развязать от Shop DB, можно перейти на событийную модель
   - B2B нужно развязать с MES, MES не должен быть источником заказов
   - выделение Order Service со своей БД - история заказов, статусы
   - retry и DLQ
   - идемпотетность
   - сверка статусов заказов между сервисами
   Почему: главная проблема бизнеса - потерянные и зависшие заказы.
   
3. Оптимизация MES
   - оптимизация запросов
   - read model
   - реплики БД, чтобы снизить нагрузку
   - внедрение кэшей
   Почему: именно MES и API сейчас создают жалобы операторов и клиентов.

4. Процессы и команда
   - Автоматизация E2E-тестов и автодеплой в release.
   - QA перевести на автоматизацию, можно нанять второго QA, чтобы помогал с текущим процессом тестирования
   Почему: долгие процессы релиза мешают быстрым доставкам до прода и доработкам

5. Отказоустойчивость
   - нужны реплики для БД
   - нужен балансировщик перед приложениями
   - s3 может забиться, если не управлять жизненным циклом заказов - можно переводить модели по завершенным заказам в холодное хранилище
   - внедрение retry, rate limiter на API

### Какой вы видите целевую архитектуру через полгода
1) Внедрен мониторинг, логирование, трейсинг, по любому заказу можно отследить его путь через системы
2) Проведена оптимизация MES:
   - MES не должен быть источником заказов
   - read model, оптимизированы запросы
   - внедрение кэшей
   - реплики БД на чтение
3) Изменения в потоке заказов:
    - B2B API развязана с MES, MES не является источником заказов
    - Нужен один сервис, ответственный за флоу заказа (Order Service), который через событийную модель взаимодействует с остальными сервисами. Таким образом флоу заказа может выглядеть так:
        - Заказ создается в B2B API или Shop API, отправляется в очередь заказов с помощью outbox паттерна
        - Order Service читает очередь, отправляет заказ на обработку в MES, читает другую очередь в ответ, отправляет обновления по заказу в другие сервисы.
    - При этом везде нужны retry, outbox паттерн, гарантия доставки
4) Реплики БД, несколько инстансов приложений, балансировщики, 
5) Автоматизированные e2e тесты, автодеплой в release


### Если бы у вас была возможность выполнить только три пункта из списка инициатив в ближайшие полгода, что бы вы выбрали и почему
1) Внедрен мониторинг, логирование, трейсинг, по любому заказу можно отследить его путь через системы - необходимо сначала реализовать возможность узнавать, где сейчас заказ, в каком статусе, есть ли ошибки и их причину
2) Изменения в потоке заказов - необходимо решить проблему с исчезновением заказов
3) Проведена оптимизация MES - решить проблему операторов с медленным MES
