## Архитектурное решение по логированию

### Анализ диаграммы
1) Логи нужны из систем - API, сервисы, БД, rabbitMQ

Общие поля всех записей: timestamp, level, service, env, trace_id, span_id, order_id, client_id

1) Создание заказа - orderId, clientId, канал (B2C/B2B), источник
2) Изменение статуса заказа - orderId, from_status, to_status, инициатор
3) Загрузка 3D-модели - orderId, ключ объекта в S3, размер, количество полигонов
4) Постановка расчёта стоимости в очередь - orderId
5) Завершение расчёта стоимости - orderId, длительность
6) Публикация сообщения в очередь - orderId, queue, messageId
7) Получение сообщения из очереди - orderId, queue, messageId, номер попытки
8) Подтверждение производства продавцом - orderId, id продавца
9) Взятие заказа оператором - orderId, id оператора
10) Вызов внешнего B2B API - client_id, endpoint, длительность, код ответа

Уровни логирования
- ERROR - сбой, требующий вмешательства: ошибка обработки сообщения, уход в DLQ, недоступность S3, падение расчёта стоимости
- WARN - деградация: retry сообщения, повторная доставка, превышение порога длительности расчёта, SLA заказа
- INFO - бизнес-события из списка выше
- DEBUG - выключен в prod, включается точечно при разборе инцидента через изменение уровня без редеплоя
- TRACE - не используется

### Мотивация
Логирование позволить создать основу для решения нескольких проблем компании:
1) Выявить системы, нуждающиеся в оптимизации
2) Сэкономить время и ресурсы на выявление и устранение проблем в случае сбоев и багов
3) Повысить общее качество и надежность систем

Позволит отслеживать следующие метрики:
1) Доля повторных обращений по одной и той же проблеме
2) доля инцидентов, локализованных поддержкой без эскалации на разработку
3) доля ошибок, обнаруженных по ERROR-логам раньше, чем по жалобе

Внедрение логов необходимо реализовать в следующем порядке:
1) Логирование на API - достаточно дешево, покрывает большую часть пути заказа и прочих пользовательских запросов
2) Логирование в MES - важный сервис для флоу заказа, нужно понимать какие проблемы с заказами возникли
3) Логирование RabbitMQ - место взаимодействия части сервисов, нужно знать состояние брокера, DLQ и прочее.
4) Все остальное - БД, s3 и прочее

### Предлагаемое решение
1) Для внедрения логирование необходимо доработать все API, сервисы и прочие компоненты.
2) В качестве технологии предлагается использовать стэк ELK, как распространенное opensource-решение с большим сообществом и гайдами. Это позволит быстрее развернуть и настроить логирование.

Я не стал соединять все сервисы с filebeat, чтобы не перегружать диаграмму

### Безопасность
1) Авторизация по ролям:
   - Поддержка: поиск логов по orderId, просмотр логов.
   - Разработка и DevOps: полный доступ, включая конфигурацию.
   - Продакт и администраторы: доступа нет.
   - Операторы и продавцы: доступа нет.
2) Сетевая изоляция. ELK не публикуются в интернет, доступ только из внутренней сети или через VPN.
3) Никаких персональных данных в логировании - только обезличенный clientId.
4) Если персональные данные все же попадают - алерт и тикет на маскирование.

### Политика хранения
1) Логи хранятся 2 недели, после - переносятся в холодное хранилище на 90 дней, после - удаляются
2) DEBUG логи хранятся 7 дней, после - удаляются
3) Для бизнес-логов исключение - 14 дней хранятся, холодное хранилище - год, нужно для разбора давних ошибок
4) Для окружений dev и release исключение - 7 дней хранятся, после - удаляются
5) Индекс разделяется по классам логов - бизнес-логи, технические логи, access-логи.

### Объем
Допустим 3000 заказов в месяц, и 20 бизнес логов на каждый заказ с размером 1 КБ, тогда - 60 МБ/месяц.

### Алертинг
1) Персональные данные в логах - алерт и тикет
2) Большое количество логов типа ERROR - алерт и разбор проблемы
3) Резко возросшее количество логов - алерт и разбор проблемы
4) Отсутствие логов длительное время - алерт и разбор проблемы
