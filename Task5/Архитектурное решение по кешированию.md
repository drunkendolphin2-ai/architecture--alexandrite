## Архитектурное решение по кешированию

### Мотивация

Проблемы, которые решает кеширование:
1) Операторы жалуются на медленную загрузку списка заказов. 
2) Дашборд MES находится на критическом пути: вознаграждение получает тот, кто взял заказ первым.
3) Чтение конкурирует с записью: единственный инстанс MES DB одновременно обслуживает дашборд и запись по производству.
4) Нагрузка растёт линейно, +100 заказов в месяц. Без кеширования деградация чтения продолжится вместе с ростом.

Что планируется кешировать:
1) Индекс списка заказов - сортированный набор orderId по статусам. При создании заказа и смене статуса к набору добавляется или удаляется элемент.
2) Карточки заказов по orderId.
3) Результаты расчёта стоимости по хешу 3D-модели и параметров - данные иммутабельные, повторный расчёт одной модели не нужен.
4) Справочные данные - операторы, статусы, материалы.

Не кешируется результат выборки как таковой (сериализованная страница списка): при добавлении заказа сдвигаются все страницы сразу. Вместо этого кешируется изменяемый индекс, из которого страница собирается на лету.

Ожидаемый эффект:
1) Время загрузки списка заказов снижается, оператор видит актуальные заказы быстрее.
2) Снижается нагрузка на MES DB, чтение перестаёт конкурировать с записью.
3) Повторные расчёты стоимости не выполняются, освобождаются мощности под новые заказы.
4) Система выдерживает рост нагрузки без роста нагрузки на БД.

Кеширование не заменяет оптимизацию: на промахе запрос всё равно идёт в БД. В связке нужны оптимизация запросов, read model и реплика на чтение.

### Предлагаемое решение

#### Клиентское или серверное

Выбрано серверное кеширование, технология - Redis, поскольку нужны самые актуальные данные, возможна конкуренция за запрос на заказ.

Клиентское кеширование применяется только к справочным данным.

#### Паттерн

Для карточек заказов и результатов расчёта - **Cache-Aside**: приложение проверяет кеш, на промахе читает БД и кладёт результат в кеш.

Для индекса списка - обновление на записи (по сути write-through для индекса): при создании заказа и смене статуса orderId переносится между наборами.

Почему не Refresh-Ahead:
- он рассчитан на предсказуемый доступ и обновление по расписанию до истечения TTL;
- здесь данные меняются по событию, а не по времени, обновление за секунду до смены статуса бесполезно.

#### Стратегия инвалидации

Основная - **программная**. Кеш обновляется явно в момент изменения данных:
- создание заказа: карточка в кеш, orderId в индекс статуса;
- смена статуса: карточка обновляется, orderId переносится между индексами;
- взятие заказа оператором: orderId удаляется из индекса свободных.

Дополнительно - **временная** (TTL 5-10 минут на индекс, с разбросом) как страховка от пропущенного обновления: рестарт Redis, сбой обработчика, потеря события. По истечении набор перестраивается из БД.

Почему не подходят остальные:

| Стратегия                 | Почему не подходит как основная                                                                                                                                     |
|---------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Только временная          | Крайне важно обработать изменение статуса заказа, когда другой оператор взял заказ. В данном случае это невозможно                                                  |
| По ключу (версия в ключе) | Смена версии обесценивает весь набор целиком, а изменения статусов идут постоянно - кеш обнулялся бы непрерывно. Старые версии остаются в памяти до истечения TTL.  |
| Программная + TTL         | Выбранный вариант: актуальность обеспечивает точечное обновление, TTL ограничивает время жизни незамеченного расхождения                                            |
